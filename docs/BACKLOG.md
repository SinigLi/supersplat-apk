## #2 详细分析（2026-10-29 截图）

真机截图报错原文：

```
打开失败：'readFile' failed: Failed to allocate a 241634136 byte allocation
with 25165824 free bytes and 178MB until OOM, target footprint 240301440,
growth limit 402653184
```

**这不是文件丢失，是内存分配失败（OOM）。** 拆开看：

| 数字 | 含义 |
|---|---|
| `241634136` | 本次要一次性申请的字节数 ≈ **230 MB** |
| `25165824` | 当时堆里仅剩 ≈ 24 MB 可用 |
| `growth limit 402653184` | 该进程堆上限 ≈ **384 MB** |

**推断的根因链**：

1. `readFile` 把整个 `project.svproj` 一次性读成 **base64 字符串**。base64 膨胀 4/3，反推磁盘文件 = `241634136 × 3 ÷ 4` = **181,225,602 字节（约 173 MB）**。
2. 拿到 base64 还要解码回字节（又一份 173 MB），交给 fflate 解压（再一份），最后取出内嵌的模型字节。
3. 峰值内存远超 384 MB 上限，于是在**读取阶段**就崩了——所以现象是「打不开」而不是「保存失败」。

**代码定位（已核对 http://www/projects.js）**：

| 位置 | 代码 | 说明 |
|---|---|---|
| line 192-211 | `nativeStore.write()` | 已分块：`CHUNK = 2MB`，超过就建空文件 + `appendFile` 逐片追加 |
| line 213-221 | `nativeStore.read()` | **没有分块**：单次 `readFile()` 把整文件读回，然后 `base64ToBytes()` 一次性解码 |

写入那段的注释写得很清楚：「模型动辄 20MB+，base64 后更大。一次性过桥会撑爆 WebView 的消息通道」。**同一个问题读取侧完全没处理**——当年只防了写入方向。

所以这不是偶发，而是**必然复现**：splat 文件一大就崩，跟设备剩余内存关系不大（24 MB 剩余只是最后一根稻草，就算有 200 MB 空闲，后续解码/解压还会再来一个峰值）。

**可能的方向（周末再定，先不动）**：

- **读取也走分块**（最小改动、与写入对称）：用 Filesystem 的 `readFile` + `offset`/`length` 分段（Capacitor 7 是否支持需确认；不支持则可考虑 `readFile` 拿 native URL 后用 fetch 的 Range 读），边读边拼/边解，任何时刻不持有整份副本
- **改存储结构**（更彻底）：模型不塞进 zip，改为独立文件存放，打开时按需流式加载；顺带把 `state.json` 与模型解耦
- **两者结合**：小工程走现方案（快），超过阈值自动切分块路径

### ✅ 拍板（2026-10-29 19:54）

老板：模型是 **GLB**，选**根治方式**（改存储结构）。老板 21:56 补充：模型为 `I:\三维学习备份\GLBCMP_A_00001_.glb`，曾导入过其他多个模型但都删除了；猜想「删除不掉」或「保存多次容量递增」。

### ✅ 对账验证（2026-10-29 深夜，实尺实测）

| 项 | 值 |
|---|---|
| 模型实际体积 | 90,611,084 B = 86.4 MiB（MD5 B7C3474E63BAF4A73B85907D6609DF5E）|
| OOM 分配 | 241,634,136 B（readFile 返回的 base64 串）|
| 反推磁盘文件 | 241,634,136 × 3/4 = 181,225,602 B |
| 用同一 GLB 打「两份」zip | 181,222,814 B（与反推值差 **2,788 B**，即 state.json 差异）|
| 打「一份」zip | 90,611,632 B（差一倍，排除）|

**结论：工程文件 = 同一个 GLB 完整存了两份（props/0.glb + props/1.glb）。** 场景里有 2 个同模型的道具实例（疑似导入过两次）；zip level 0 不压缩，两份完整字节直接相加。数字闭合到 2.8KB。

**对老板两个猜想的回答**：

1. **「删除不掉」→ 文件层面不成立**：文件里只有 2×GLB + 2.8KB 状态，没有其他模型的字节——删掉的模型确实没被保存进文件。但 #4 的 UI 问题是真实的：资产列表删除按钮点了没反馈，导致「看起来没删掉」。
2. **「保存多次递增」→ 不成立**：保存是全量重写 zip，不追加；多次保存体积不变。两份从一开始就在（两次导入各存一份）。

**顺带发现的次生问题（一并修）**：两实例在内存里也各持一份 `sourceBytes`（2×86.4 MiB 常驻）——修复时同 blob 恢复应共享同一 Uint8Array 引用。

**顺带一个观察（已确认是真 bug，但原因和我最初猜的不一样）**：列表里这个工程标着「空工程」，可文件有 173 MB。

原因不是「回写缺失」，而是 `hasModel` 的判定口径太窄：

```js
// projects-ui.js
hasModel: !!snap.model
```

而 `snap.model` 只来自 `director.projectModel()`，那个方法只认 **splat 元素**（`ElementType.splat` + `sourceBytes`）。GLB 在导演台里是**道具**，走的是 `projectPropFiles()`，根本不进 `snap.model`。

所以：**纯 GLB 工程必然显示「空工程」**，哪怕里面塞了 173 MB 的道具。修 #2 时一并改判定口径（把 props 也算进去）。

### ⚠ 真机首开报 Missing parent directory（2026-10-30，v29 首发版）

v29 包真机打开旧工程报 `打开失败：Missing parent directory – possibly recursive=false was passed or parent directory creation failed`。

根因：迁移首块走 `appendFile` 往 `files/.tmp-N.part` 写，父目录 `files/` 尚不存在。Capacitor Filesystem 的 appendFile 在 Android 端走 writeFile 同一实现，`recursive` 不传就不建父目录（Kotlin 源码 FilesystemPlugin.kt `getWriteFileOptions` 读 `recursive` → IONFILESaveOptions）。桌面/测试端 web store 没有目录概念，测不出来——又一次「桌面绿 ≠ 真机过」。

v29b 修复：所有 appendFile 带 `recursive:true`；迁移首块 flush 先 write 空文件（建档 + 建父目录 + 截断上次中断的残尾 .tmp）；新增 tests/probe-v29-migrate.mjs 端到端验证流式迁移（去重/字节一致/旧 zip 删除）。
